Markdown
    
    
    # （问题卡）如何定位慢 SQL：一套排查路径  
      
    ## 一句话结论  
    先用慢日志/监控确认“慢在 DB 还是慢在应用”，再用 EXPLAIN 判断是否走索引、扫描行数与 filesort/temporary，最后决定改 SQL、加索引还是改模型。  
      
    ## 触发场景  
    - 现象：接口 RT 升高，DB CPU 或 IO 异常  
    - 影响：核心查询接口  
    - 环境：MySQL（常规 OLTP）  
      
    ## 排查路径（Checklist）  
    - [ ] 是否命中慢查询日志（阈值、采样、时间窗口）  
    - [ ] 是否 DB 资源异常（CPU/IO/连接数/锁等待）  
    - [ ] EXPLAIN：type / rows / key / Extra 是否异常  
    - [ ] 是否出现 Using filesort / Using temporary  
    - [ ] 是否回表（覆盖索引是否可行）  
    - [ ] 是否事务过长/锁等待导致“看起来慢”  
    - [ ] 是否参数/数据分布导致索引失效（函数、隐式转换、低选择性）  
      
    ## 常见原因 → 对应动作  
    - 联合索引不匹配 → 调整索引顺序/改写 where 条件  
    - 排序+分页深翻页 → 延迟关联/游标分页/限制翻页  
    - 回表成本高 → 覆盖索引/减少返回列  
    - 锁等待 → 缩短事务/补索引/拆分热点更新  
      
    ## 适用边界  
    - 适用：典型 OLTP 表与查询  
    - 不适用：分析型复杂查询需要结合执行引擎与数据分片策略  
      
    ## 关联入口  
    - 技能：[[SQL-性能优化-MOC]]

### 3.2 示例：概念卡（覆盖索引）

新建：`10-Notes/示例-概念卡-覆盖索引.md`

Markdown
    
    
    # （概念卡）覆盖索引：为什么能减少回表  
      
    ## 一句话结论  
    查询需要的列如果都在索引里，MySQL 可以直接从索引返回结果，减少“回表”读取主键记录的成本。  
      
    ## 我自己的解释（禁止抄定义）  
    索引像“目录”。普通情况你先从目录定位到书页（主键记录），再去翻书；覆盖索引相当于目录里就写了你要的内容，你不用再翻书。  
      
    ## 常见误区  
    - 误区1：有索引就一定快 → 正解：可能仍要回表/扫描行数大/排序临时表  
    - 误区2：覆盖索引越多越好 → 正解：索引多会带来写入成本与空间成本  
      
    ## 最小示例  
    ```sql  
    -- 订单表 (user_id, status, created_at, amount, ...)  
    -- 查询只需要 user_id/status/created_at  
    -- 建索引 (user_id, status, created_at) 可能成为覆盖索引  
    select user_id, status, created_at  
    from orders  
    where user_id = ?  
      and status = ?  
    order by created_at desc  
    limit 20;

## 何时用 / 何时不用

  * • 用：读多写少、热点查询、返回列少且稳定
  * • 不用：写入非常频繁/列变化很大/索引膨胀严重

    ### 3.3 示例：方案卡（订单查询缓存选型）  
    新建：`10-Notes/示例-方案卡-订单查询缓存选型.md`  
      
    ```markdown  
    # （方案卡）订单查询缓存：在高峰期降低 DB 压力（可灰度可回滚）  
      
    ## 一句话结论  
    选择 Redis + 失效策略 + 热点保护，因为跨实例收益最大且可灰度回滚；一致性以“可接受不一致窗口”为边界来控制风险。  
      
    ## 背景与约束  
    - 目标：高峰接口 RT < 100ms；DB CPU < 60%  
    - 约束：两周上线；必须可回滚；需要补齐监控  
      
    ## 方案对比  
    ### 方案A：本地缓存  
    - 优点：延迟低、实现简单  
    - 缺点：多实例一致性差；重启抖动；容量受限  
    - 风险：热点集中导致单机抖动  
    - 适用条件：实例少、弱一致要求  
      
    ### 方案B：Redis 缓存  
    - 优点：跨实例共享；容量与淘汰可控；可统一治理  
    - 缺点：引入外部依赖；一致性需要策略  
    - 风险：穿透/击穿/雪崩  
    - 适用条件：读多写少，允许短暂不一致  
      
    ## 决策  
    - 选择：Redis  
    - 关键理由（Trade-off）：  
      1. 整体收益覆盖所有实例与链路  
      2. 灰度与回滚简单可控  
      3. 风险可通过热点保护与监控兜底  
      
    ## 落地与回滚  
    - 灰度/回滚：按用户维度灰度；开关控制读写；异常一键切回直读 DB  
    - 监控指标：命中率、DB QPS、接口 RT、错误率、Redis 延迟、热点 key  
    - 验收标准：指标达标且灰度期无新增事故  
      
    ## 关联入口  
    - 技能：[[Redis-缓存与一致性-MOC]]  
    - 项目：[[P-项目名-首页]]

### 3.4 示例：复盘卡（接口超时事故）

新建：`10-Notes/示例-复盘卡-接口超时事故.md`

Markdown
    
    
    # （复盘卡）接口超时：下游抖动导致线程池耗尽  
      
    ## 一句话结论  
    根因是下游 RT 抖动 + 缺乏隔离与超时控制，导致线程池被占满；关键改进是增加超时/隔离/熔断与线程池监控告警。  
      
    ## 事实（发生了什么）  
    - 10:02：接口 RT 上升，开始出现超时  
    - 10:05：错误率升高，用户下单失败  
    - 10:08：定位到下游依赖 RT 抖动  
    - 10:20：临时降级后恢复  
      
    ## 机制（为什么会这样）  
    - 根因：下游调用缺少有效超时/隔离，慢请求占用线程  
    - 放大器：线程池队列增长、拒绝策略不合理导致雪崩扩大  
    - 为什么没提前发现：线程池 active/queue/reject 未纳入告警；缺少依赖维度 RT 告警  
      
    ## 改进（下次怎么做）  
    ### 规则/清单（可复用）  
    - [ ] 下游调用必须设置超时 + 重试上限，并区分幂等与非幂等  
    - [ ] 关键依赖必须隔离（线程池/舱壁）并提供降级路径  
    - [ ] 线程池必须监控：active、queue、reject、任务耗时分位数  
      
    ### 行动项  
    - [ ] 补齐线程池监控与告警（owner：__，DDL：__）  
    - [ ] 为关键依赖增加降级开关（owner：__，DDL：__）
