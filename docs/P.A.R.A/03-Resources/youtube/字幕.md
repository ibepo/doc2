All right, with that out the way, let's get into phase one of starting a new Claude code project, and that's planning.

We're going to cover the two most important questions to ask yourself, how to create a project spec doc that captures both product and engineering requirements, and how to use AI to help you plan at every step of the way. And look, I get it. Planning sounds boring. You want to start coding, but trust me on this one. Spending just 15 minutes planning your project up front will save you hours, sometimes even days, of frustration down the line. Now, before I even open Claude Code, I do a brainstorm of what I want to achieve with the project. Specifically, I ask myself two questions and note down the answers using a pen and paper or a Google doc.

The first question that I ask myself before building is: what are you actually trying to do, or what is the goal of your project? Are you trying to learn a new technology? Are you trying to validate an idea with customers? Are you building an alpha version of a product or feature? Or are you just prototyping to see if something is possible? Getting clear about what you're actually trying to do changes everything about how you approach the project. It tells you what's important to build versus what you can skip. For example, if you're just trying to prototype to see if a feature is a good idea, you can just focus on the core functionality for that feature. You don't need to worry about production-ready code or edge cases. You can move fast and break things. But if you're building something you want to ship to real users, then you need to think about things like security, error handling, edge cases, and all the details that make your product feel polished. A key thing to keep in mind when you're planning is that the clearer you are, the better Claude will understand what you're trying to achieve and build accordingly.

The second question I ask myself in the plan phase is: what are the milestones of functionality that you want? This is where you can start breaking down your project into clear phases. What does version one look like? Maybe it just focuses on one core feature. What are you okay with leaving out or saving for future versions? And then you can apply that same thinking to version two, version three, and so on. For most projects, I like to think in terms of an MVP or minimum viable product, and then one or two versions of improvements. The MVP is the absolute minimum you need to validate your idea or prove that the concept works. And then in future versions, you can add things like scaffolding, polish, or optimizations.

Next up in phase one is using AI to help you plan. Once you have your brainstorm, this is where you can use AI to help you flesh out the plan for your project. And here's my pro tip for using any AI to help you plan: tell it to ask you questions. For example, when I start a new project, I give Claude my brainstorm in a markdown file and ask, “Hey, Claude, I want to build this project. What are the three most important questions I need to answer in order to build an MVP of this successfully?” Claude will then ask me clarifying questions about the brainstorm to help me spot things that I haven't fully thought through. It will ask things like: who is the user? What is the core problem? What platforms are you targeting? What technical constraints or preferences do you have? What are success criteria? This question-asking step helps you catch blind spots early and produce a better spec.

Once you’ve answered those questions, you can have Claude help you draft a combined product-and-engineering spec. I like to structure it with: overview and goals, user stories and scenarios, requirements (must-have vs nice-to-have), architecture and data model, APIs and integrations, non-functional requirements (performance, security, observability), and acceptance criteria for the MVP. The output should be specific enough that Claude Code can start building without guessing. If you include example payloads, model fields, and endpoint shapes, you’ll get much better results.

Now let’s move on to phase two: setup. This is where you configure Claude Code with everything it needs to build effectively. I use a seven-step setup checklist for Claude Code. First, set up a GitHub repo with the right structure for your stack (web or mobile) and decide upfront that you’ll do issue-based development — open issues for features or bugs, and use branches named after issues. Second, create your environment variable file (.env) and document the keys needed for local development, staging, and production. Third, add a CLAUDE.md (or claw.md) file to the repo. This file explains the project, stack decisions, coding conventions, and how to run/test the project. It’s the onboarding doc for Claude Code. Fourth, set up automated project documentation — README sections for setup, scripts, and troubleshooting; a docs/ folder with architecture notes; and enable a doc generator or use Claude to maintain docs as code changes. Fifth, install plugins you need for your workflow, such as file system, GitHub, or frameworks helpers. Sixth, install MCP servers for tools like databases, HTTP clients, or special capabilities so Claude can interact with your environment. Seventh, set up custom slash commands and sub-agents for common tasks — for example /scaffold page, /write test for module, or specialized agents for frontend, backend, and docs.

For advanced setup, I also preconfigure permissions so Claude Code has the right access to repositories and tools without constant prompts, and I add hooks — like pre-commit hooks, CI checks, and code formatters — to keep quality consistent.

Phase three: build. Start by building your MVP directly from the spec. I use three development workflows. Workflow 1: single feature development — pick one feature, open an issue, let Claude Code plan the steps (files to edit, tests to write), implement, test, and merge. Workflow 2: issue-based development — keep everything organized by issues; each issue describes scope, acceptance criteria, and testing steps. Claude Code can move the issue through states and open PRs. Workflow 3: multi-agent development (multi-Clauding) — run multiple Claude instances or use Git worktrees so different agents can tackle separate features in parallel without stepping on each other’s changes.

A few tips for building productively: keep the spec updated as you learn; write tests first or at least alongside features so Claude Code has clear validation; chunk work into small, reviewable steps; use logs and monitoring even in MVPs to catch issues early; and periodically refactor with Claude’s help to reduce tech debt.
